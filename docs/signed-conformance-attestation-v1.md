# Signed conformance attestation v1

R10 authenticates the origin of a R9 conformance claim without changing the R9 artifact or requiring cryptography inside HOWEDO core.

## Evidence stack

```text
runtime execution
      ↓
R9 conformance artifact
      ↓
R9 core verification
      ↓
in-toto Statement/v1
      ↓
R10 semantic binding verification
      ↓
Sigstore keyless signature bundle
      ↓
signer identity + transparency verification
```

## Build a statement

Given a valid R9 artifact:

```bash
howedo-build-attestation artifact.json artifact.intoto.json
```

The generated statement has:

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "howedo.adapter-conformance-artifact.v1",
      "digest": {
        "sha256": "<R9 artifact digest without sha256: prefix>"
      }
    }
  ],
  "predicateType": "https://github.com/nulleimy/HOWEDO/attestations/adapter-conformance/v1",
  "predicate": {
    "adapter": {
      "adapterId": "...",
      "adapterVersion": "...",
      "manifestDigest": "sha256:...",
      "runtimeFamily": "..."
    },
    "artifactVersion": "howedo.adapter-conformance-artifact.v1",
    "conformance": {
      "checkCount": 11,
      "passedCount": 11,
      "status": "CONFORMANT"
    },
    "evidenceRefs": []
  }
}
```

The builder refuses an R9 record that fails `verify_conformance_record()`.

## Verify semantic binding

```bash
howedo-verify-conformance artifact.json
howedo-verify-attestation artifact.json artifact.intoto.json
```

The second command checks:

- exact Statement v1 type;
- exact single subject;
- exact subject SHA-256 binding to the R9 artifact;
- exact HOWEDO predicate type;
- exact predicate projection from the R9 artifact;
- absence of unexpected statement fields.

This is semantic verification only. It deliberately does not claim cryptographic issuer authentication.

## Reference keyless signing

The GitHub Actions reference pipeline signs each generated statement with Cosign using GitHub OIDC:

```bash
cosign sign-blob --yes \
  --bundle artifact.sigstore.json \
  artifact.intoto.json
```

The signing job receives `id-token: write`; other conformance jobs do not.

The reference pipeline stores no long-lived private signing key.

## Reference cryptographic verification

A signed statement is verified against the expected GitHub workflow identity and issuer:

```bash
cosign verify-blob artifact.intoto.json \
  --bundle artifact.sigstore.json \
  --certificate-identity "$EXPECTED_WORKFLOW_IDENTITY" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  --certificate-github-workflow-repository "$EXPECTED_REPOSITORY" \
  --certificate-github-workflow-sha "$EXPECTED_WORKFLOW_SHA" \
  --certificate-github-workflow-ref "$EXPECTED_WORKFLOW_REF" \
  --certificate-github-workflow-trigger "$EXPECTED_EVENT"
```

A consumer must set the expected identity values from its trust policy. Accepting arbitrary certificate identities is not a HOWEDO verification policy.

## Complete acceptance rule

A signed conformance claim is accepted only when:

1. `howedo-verify-conformance` passes for the R9 artifact;
2. `howedo-verify-attestation` passes for the artifact + statement;
3. Sigstore/Cosign verification passes against the consumer's expected signer policy.

No one check substitutes for another.

## CI output

The R10 reference job consumes the four R9 artifacts generated by the LangGraph and Temporal jobs on Python 3.12 and 3.13. For each artifact it emits:

```text
<runtime>-py<version>.json
<runtime>-py<version>.intoto.json
<runtime>-py<version>.sigstore.json
```

The combined GitHub Actions artifact is named:

```text
howedo-signed-conformance-attestations
```

## Trust boundary

R10 authenticates the signed statement through the selected external trust system. It does not grant execution authority and does not convert conformance into authorization.

HOWEDO remains responsible for continuity semantics. Sigstore remains responsible for the reference signing and certificate/transparency verification path.
